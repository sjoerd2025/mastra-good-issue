# Feature Request Template

Use when the target project has no issue template. Lead with the problem, not the solution.

```markdown
## Problem

<!-- The workflow that is currently impossible or painful. Concrete, not abstract.
     "I need to X, but currently Y" — never open with a proposed API. -->

## Current workaround

<!-- What you do today and why it's inadequate. Include code if short.
     "None found" is valid and strengthens the request. -->

## Proposed solution (optional)

<!-- A sketch, explicitly marked as one possible approach. Maintainers often know
     a better fit for their architecture — the problem statement is what matters. -->

## Prior art

<!-- How comparable libraries solve this, with links. -->

## Contribution

<!-- e.g. "Happy to implement this if the approach sounds right — let me know." -->
```

## Guidance

- One request per issue. Split bundled asks.
- Search closed issues and discussions first — feature requests are frequently
  rejected with reasoning worth reading; link and address it if so.
- Check if the project prefers Discussions/RFCs for feature ideas and use that
  channel instead if so.
- Scope it falsifiably: a maintainer should be able to say unambiguously when
  it's done.
